# VoiceReach hardening round 2: roadmap and spec

This is the spec for eight phase plans (`2026-10-23-01-*.md` to `2026-10-23-08-*.md`).
It comes from the 2026-10-22 four-part audit (mobile, backend pipeline, AI/RAG/voice,
data/security/ops). Goal: fix every item the audit judged a **shortcut** or
**right only at demo scale**, so every remaining decision can be defended as
deliberate. Each phase plan is a self-contained implementation plan. Executors
read this file first, then their phase plan.

## Owner decisions (2026-10-23)

1. **Sign-in stays as it is.** The app keeps auto-signing in as the shared demo
   account (`mobile/services/supabase.ts:8-9`). Out of scope: per-worker accounts,
   roles, multiple organisations, an app lock / Face ID, removing the hardcoded
   password. Phase 8 documents this as a known limitation in README.
   Encrypting the stored session (Phase 6) is in scope because it doesn't change
   how sign-in behaves.
2. **Code only.** Agents write migrations, SQL functions and config. They never
   apply anything to the hosted Supabase project or Railway. Every step that needs
   the owner goes into `docs/superpowers/plans/2026-10-23-manual-steps.md` (see below).
3. **Voice:** streaming playback, streaming the mic over the existing proxy,
   barge-in, and read-only tool calling for retrieval. **No WebRTC.** The backend
   proxy stays the security boundary.
4. **Phased, all written now.** Agents then run the plans in order.

## Global constraints (every task in every phase)

  import. Recreate it first:
  `python3.11 -m venv .venv && source .venv/bin/activate && python -m pip install -r requirements.txt -r requirements-dev.txt`.

  root, offline), `ruff check backend --select F,E9`, `cd mobile && npx tsc --noEmit && npx jest`.

  `backend/tests/helpers.py` fakes (`FakeSupabase` is strict: an unscripted query
  fails the test). When a phase adds `supabase.rpc(...)` calls, it extends the fakes
  to script `rpc` the same strict way (Phase 2 owns that change).
- **CLAUDE.md rules still hold:** no unauthenticated routes (only `/health` is
  open); never reintroduce `skin_color`; never call `supabase.from` in `mobile/`;
  all data goes through the backend; no PII in logs (`backend/tests/test_no_pii_logs.py`,
  `mobile/test/noDataLogs.test.ts`); database text reaches a model only as a
  delimited `user` item or a delimited tool output, never as a `system` message.
- When a phase changes a rule that CLAUDE.md or README states (recording format,
  duplicate behaviour, urgency, upload format, assistant behaviour), the same task
  updates CLAUDE.md and README.
- **Database changes:**
  - Each change is a new file in `supabase/migrations/` named
    `2026110P0000SS_<snake_name>.sql`, where P is the phase number and SS a sequence
    number (Phase 2's first file is `20261102000001_...`).
  - Migrations must be idempotent (`IF NOT EXISTS`, `CREATE OR REPLACE`).
  - The same change is folded into `supabase/schema.sql`, which stays the full
    current schema for a fresh database.
  - `backend/tests/test_schema_contract.py` and `test_schema_sql.py` must keep passing
    and be extended for new objects.
  - Every migration gets a line in the manual-steps file.
- **Git:**
  - Work on branch `hardening-2` (create it from `main` if it doesn't exist; never
    commit to `main` directly).
  - One commit per task, conventional prefix (`feat:`, `fix:`, `refactor:`,
    `test:`, `docs:`, `ci:`), ending with
    `Co-Authored-By: Claude Opus 5.5 (1M context) <noreply@anthropic.com>`.
  - Never commit `.env` files or keys.
  - Never push to `jasonyi33/voicereach` (upstream). Pushing at all is the owner's call.

  the manual-steps file and does not block on it.
- Keep it simple: no new infrastructure services (no Redis, no Celery, no new hosted
  queues). Where the audit suggested Redis or a job queue, the plans use Postgres
  plus the existing single process (see Phase 7).
- Comment density, naming and style match the surrounding code (short "why"
  comments, audit codes such as `(C-26)` where relevant; new items use the code
  `H2-<phase>.<n>`, for example `(H2-1.3)`).

## The manual-steps file

`docs/superpowers/plans/2026-10-23-manual-steps.md`, which Phase 1 creates.
Sections: **Apply migrations** (in order), **Environment variables** (name, default,
which service), **Device checks** (numbered steps with expected results),
**Owner actions outside code** (OpenAI zero data retention and BAA, confirming the
leaked keys in git history are revoked, EAS project init, App Store bundle id).
Each phase appends to it, under exactly those four `##` headings (no new sections):
**Apply migrations** is one numbered list in filename order; **Environment variables**
adds rows to Phase 1's table (`| Name | Default | Service | Phase |`); **Device checks**
entries keep their phase's id prefix (`D5.n`, `P7-n`, `(H2-6.n)`, ...). If the file is
missing (Phase 6 ran early on a branch without it), create it from Phase 1 Task 1's text.

## Phases, order and dependencies

```
P1 backend runtime ─┬─> P2 data integrity ─┬─> P3 AI quality ─────────┐
                    │                      ├─> P4 search & retrieval ─┼─> P5 voice & audio
                    │                      └───────────────────────────┴─> P7 async recordings + offline queue
                    └─> P6 mobile robustness & privacy (mobile-only; can run beside P2-P4)
P8 ops, CI & release: last
```

**Run the phases one at a time in this order: P1, P2, P3, P4, P5, P6, P7, P8.** This
satisfies every dependency and settles each "if Phase X landed first" branch in the plans
(P5 always lands before P6; P2 always before P6). P3 and P4 must not run in parallel: both add
a `MIGRATIONS` constant to `test_schema_sql.py`. P5 needs P4's retrieval functions.
P7 needs P2 (idempotency, RPCs), P3 (the pipeline functions) and P6 (TanStack
Query and the error boundary).

## Phase 1: backend runtime correctness

Plan: `2026-10-23-01-backend-runtime.md`. Backend only.

1. **The event loop is blocked by sync supabase-py calls** inside `async def`
   (`transcription.py:79`, `duplicate_detection_service.py:135-148`, all of
   `individual_service.py`, `embeddings.py:113,122`, `categories.py:231`). This stalls
   every request and the realtime proxy (`main.py:334-357`).
   - Fix: every `.execute()` reached from an async path runs off the loop through one
     helper, `backend/db/client.py: async def run_db(fn: Callable[[], T]) -> T`, built on
     `starlette.concurrency.run_in_threadpool` (the pattern `context_service.py:186` already uses).
   - Sync `def` routes are already run in a threadpool by FastAPI; leave them sync.
2. **One shared client per process.**
   - `backend/db/client.py: get_supabase() -> Client` builds the service-key client
     once (lazily, so tests can patch it) and is the only `create_client` call for the
     service key. It replaces `transcription.py:73`, `individuals.py:42-54`,
     `categories.py:71,115,180`, `embeddings.py:43-52`, `voice_assistant.py:27`,
     `main.py:159`. `api/auth.py` keeps its own anon-key client.
   - The PostgREST timeout is set below the route deadline: 20 s, via
     `ClientOptions(postgrest_client_timeout=20)`.
   - `OpenAIService` becomes a module-level singleton,
     `services/openai_service.py: get_openai_service() -> OpenAIService`.
3. **PostgREST silently stops at 1,000 rows** (`individual_service.py:371`, export
   `categories.py:77`, rescore `individual_service.py:74`, `embeddings.py:113,121`,
   generate-all).
   - Fix: `backend/db/client.py: def fetch_all(build: Callable[[], Any], page_size: int = 1000) -> list[dict]`.
     It re-runs `build().range(start, start + page_size - 1).execute()` until a short page.
   - Search's text leg keeps its own result limit.
4. **Error mapping:**
   - Pydantic `ValidationError` subclasses `ValueError`, so `individuals.py:166` and
     `transcription.py:152` turn bad database rows into 400s that echo values. Catch
     `pydantic.ValidationError` first and return `internal_error`.
   - The merge race at `individual_service.py:262` (`update_response.data[0]` on a
     deleted row) returns 404, not an IndexError 500.
   - `db/models.py:37` still prints a Python list for missing fields; use commas,
     matching 83e7d37.
5. **Body and field limits:**
   - `BODY_LIMITS` (`main.py:85-89`) adds `POST /api/individuals` at 256 KB. There is
     no `PUT /api/individuals/{id}`: a merge is the same POST with `merge_with_id`.
   - `SaveIndividualRequest.transcription` gets `max_length=20000`; `data` at most 100 keys.
6. **Public `/docs` and `/openapi.json`:** off unless `ENABLE_API_DOCS=1`
   (`main.py:65`). `/` (`main.py:166`) is removed or put behind auth.
7. **Rate limits:**
   - Add limits to save (`POST /api/individuals`, merges included; each save starts a paid
     embedding call), to `POST /api/categories` (re-scores everyone) and to delete.
   - Cap concurrent realtime sessions per user at 2 and per process at 20 (env vars),
     released in `finally` (`main.py:277`).
   - Key limits on user id **plus** an `X-Device-Id` header when one is present (the
     app sends a random id it creates once and stores in AsyncStorage), so one phone
     can't use up the shared account's budget. The per-process total for each bucket
     is still capped by an env var.
   - The one backend reader of the header is `backend/api/device.py`
     (`clean_device_id`, and the FastAPI dependency `get_device_id`). The header is
     optional: missing or malformed means `None`, never an error, because Phase 6 (the
     app side) may land after Phases 2-4.
   - Keep the in-memory fixed window (deliberate while there is one process; README
     says so).
8. **Model names from config.** `backend/services/model_config.py` with
   `CHAT_MODEL` (default `gpt-4o`), `TRANSCRIBE_MODEL` (default `whisper-1`; Phase 3
   changes it to `gpt-transcribe`), `REALTIME_MODEL` (default `gpt-realtime`), `EMBEDDING_MODEL` (default
   `text-embedding-3-large`), each read from an env var of the same name. This replaces
   the hardcoded names at `main.py:286,327`, `openai_service.py:69,222,317` and
   `embedding_service.py:24`.
9. **Typed transcription errors.** Replace the string matching at
   `openai_service.py:123-126,159-162` with checks on `openai.BadRequestError` and its
   `code`/`param`, keeping today's client messages. The assistant's message must not
   say "5 seconds".
10. **The server enforces the recording limits.** Read the M4A duration (add `mutagen`
    to requirements; `mutagen.mp4.MP4(path).info.length`) and return 400 when it is
    under 5 s or over 125 s (2:00 plus 5 s of slack). Assistant questions keep their
    own lower minimum (1 s) and a 60 s maximum.

## Phase 2: data integrity and the database

Plan: `2026-10-23-02-data-integrity.md`. Backend, SQL, and the matching mobile changes.

1. **Migrations folder.**
   - Create `supabase/migrations/` and `supabase/seed.sql`.
   - **Move the 6 demo people out of `schema.sql`** (`schema.sql:251-301`) into
     `seed.sql`, so re-running the schema never seeds production.
   - Update README and CLAUDE.md (fresh setup = schema then seed; upgrades = migrations in order).
2. **Transactional save.**
   - A Postgres function `save_individual(p_individual_id uuid, p_name text, p_data jsonb, p_urgency_score int, p_interaction jsonb, p_expected_version int, p_client_request_id uuid) returns jsonb`
     does the insert-or-update plus the interaction row in one transaction.
   - This replaces the two writes and the compensating delete in
     `individual_service.py:186-192,299-316`.
   - The backend calls `supabase.rpc('save_individual', {...})`.
   - Extend `FakeSupabase` with strict `rpc(name, params)` scripting: `on_rpc(name, data=, error=, times=)`,
     `rpc(name, params)`, `rpc_params(name) -> list[dict]` and `pg_error(code)`. Later phases use exactly these names.
3. **Optimistic concurrency.**
   - `individuals.version int NOT NULL DEFAULT 1`, incremented by the function.
   - A merge sends `expected_version`. On a mismatch the function raises SQLSTATE
     `P0409`, which the backend maps to **409** with detail
     `"This person was changed by someone else. Reload and try again."`
   - The app (`MergeUI`, `TranscriptionResults`) shows that message and re-fetches
     the person.
   - `IndividualResponse` and the profile response include `version`.
4. **Idempotent saves.**
   - `interactions.client_request_id uuid UNIQUE`.
   - The app creates one UUID per review session, sends it as the
     `Idempotency-Key` header on save, and reuses it on retry.
   - A repeated key returns the first save's result (the function checks first).
   - `mobile/services/api.ts` may then retry a save once on a network error.
5. **Merge history shows removed fields.** `changes` records a removed key as
   `{"field": null, "_removed": ["field"]}`: the merged diff gains a `_removed` list.
   `InteractionDetailModal` shows removed fields as "removed".
6. **History can't be edited.** A trigger on `interactions` raises on UPDATE.
   DELETE stays allowed, because a person's history is deleted with the person; hard
   delete is the deliberate right-to-deletion choice, and README says so.
7. **Audit log.**
   - Table `audit_log(id, at, user_id text, device_id text, action text, entity_type text, entity_id text, detail jsonb)`, with UPDATE and DELETE blocked by a trigger.
   - `services/audit.py: def record_audit(supabase, *, user_id: str, device_id: str | None, action: str, entity_type: str, entity_id: str | None, detail: dict | None = None) -> None`.
     It never raises; a failure is logged without personal data.
   - Actions: `view_profile`, `export_csv`, `delete_individual`, `override_urgency`,
     `merge_individual`, `create_individual`, `create_category`.
   - Phase 1's device id is passed through: routes take `Depends(get_device_id)` from
     `backend/api/device.py` (no second helper). It is `None` until the app sends the header.
8. **Urgency scale.**
   - `categories.number_scale_max numeric NULL`.
   - The number formula becomes `min(value / (number_scale_max or 300), 1) * weight`,
     so today's behaviour is unchanged when the column is null.
   - `CategoriesScreen` gets an optional "Scale max" input for number categories.
   - Update CLAUDE.md's urgency rule.
9. **Batched re-scoring.**
   - `rescore_all_individuals` reads with `fetch_all` and writes in batches of 500
     through an `upsert`, or a `rescore_batch(p_rows jsonb)` function.
   - `POST /api/categories` runs it as a `BackgroundTask` after answering, so the
     request no longer waits on N updates.
10. **Indexes.** `CREATE EXTENSION IF NOT EXISTS pg_trgm`; a GIN trigram index on
    `individuals.name`; an index on `interactions(client_request_id)` (from its
    unique constraint).
11. **Location privacy.**
    - The function `coarsen_old_locations(p_days int DEFAULT 30)` rounds
      `interactions.location` lat/lng older than `p_days` to 3 decimals (about 110 m).
    - Keeps the newest interaction's exact point and the person's `last_location`.
    - A commented-out `pg_cron` schedule plus a manual step for the owner to enable it.
    - README privacy section updated.

## Phase 3: AI quality and evals

Plan: `2026-10-23-03-ai-quality.md`. Backend plus a small MergeUI change.

1. **Structured Outputs for categorisation.**
   - `services/category_schema.py: def build_extraction_schema(categories: list[dict]) -> dict` builds a strict
     JSON Schema from the categories: `single_select` as an `enum` of option labels
     plus null, `multi_select` as an array of enums, `number` as number or null, text
     as string or null.
   - Every field also gets an `evidence` string: the exact transcript words it came from.
   - `categorize_transcription` uses `response_format={"type":"json_schema","json_schema":{"name":"extraction","strict":True,"schema":...}}`
     and temperature 0.
   - Delete the repair code the schema makes unnecessary (`openai_service.py:239-292`),
     but keep `validate_categorized_data` as the server-side gate.
2. **Prompt fixes.**
   - Remove the "medical conditions may be implied" rule (`openai_service.py:212`).
     Extract only what is said.
   - Resolve the "always attempt required fields" versus "be conservative" conflict
     in favour of conservative: a missing required field shows up as
     `missing_required`, never as a guess.
   - Pass the transcript as its own `user` message wrapped in
     `<<<TRANSCRIPT ... >>>` and marked as data in the system message.
3. **Drop values without evidence.** A value whose `evidence` isn't a
   case-insensitive substring of the transcript (after whitespace normalisation) is
   dropped and counted. Numbers get a lenient check: the digits or the number word
   must appear.
4. **Transcription model.**
   - `TRANSCRIBE_MODEL` defaults to `gpt-transcribe` (whisper-1 retires
     2027-02-26). Every consumer (Phase 3's transcription, Phase 5's realtime input
     transcription) reads `model_config.TRANSCRIBE_MODEL`; none hardcodes a model name.
   - Accept a `prompt` built from SF neighbourhood and street vocabulary (a static
     list in `services/transcribe_vocab.py`). **No person names in the prompt**
     (privacy).
   - Errors stay typed (Phase 1).
5. **Duplicate detection.**
   - Candidate retrieval moves into the RPC
     `find_duplicate_candidates(p_name text, p_limit int DEFAULT 50) returns setof individuals`,
     using `similarity(name, p_name) > 0.3 OR name % p_name` plus a token ILIKE.
     It replaces the 200-row scan and the OR-ILIKE query (`duplicate_detection_service.py:134-149`).
   - Add Double Metaphone (`jellyfish` package) and Jaro-Winkler to the pre-rank in
     `_rank_candidates`.
   - The compare prompt sends only name, aka, age, height, weight, gender and last
     location area. **No medical or other sensitive fields.**
   - Return the **top 3** matches of 60 or more, best first. Update
     `TranscriptionResults` and `MergeUI` to show the best match with
     "Other possible matches (n)" to switch to. Update CLAUDE.md's duplicates rule.
   - Use `DUPLICATE_MODEL` (default `gpt-4o-mini`).
6. **Duplicate labels.**
   - Table `duplicate_decisions(id, at, candidate_id, matched_id, confidence int, decision text CHECK in ('merged','saved_new'), model text)`.
   - Recorded by the save path when the review screen had a match (the app sends
     `duplicate_decision` on save).
7. **Eval harnesses** in `backend/evals/`. Offline by default, using cached model
   responses in `backend/evals/fixtures/*.json`. A live mode needs `EVAL_LIVE=1` and an
   API key.
   - `eval_extraction.py`: about 30 synthetic transcripts with expected fields.
     Reports per-field precision and recall and the hallucination rate.
   - `eval_duplicates.py`: about 40 labelled pairs. Reports precision and recall at
     thresholds 50/60/70/80.
   - All synthetic data, no real people.
   - A pytest wrapper runs the offline mode in CI and fails if a metric drops below
     the stored baseline in `backend/evals/baseline.json`.
8. **Sensitive categories.**
   - `categories.is_sensitive boolean NOT NULL DEFAULT false`, backfilled true for
     keys matching `hiv|medical|substance|mental|diagnos|pregnan`.
   - Sensitive fields are left out of duplicate prompts (item 5) and embedding text
     (Phase 4).
   - `CategoriesScreen` gets a toggle.
   - **Weights:** `create_category` rejects a weight or auto-trigger on a sensitive
     category with 400 `"Sensitive fields can't affect urgency."` (HUD CPD-17-01).

## Phase 4: search and retrieval

Plan: `2026-10-23-04-search-retrieval.md`. Backend, SQL, and the Search screen.

1. **pgvector.**
   - Migrate `individual_embeddings.embedding` from JSONB to `halfvec(3072)`: add a
     column, cast with `(embedding::text)::halfvec`, swap, and add an HNSW index
     `USING hnsw (embedding halfvec_cosine_ops)`.
   - Add `model text`, `text_hash text` and `source_updated_at timestamptz`.
   - Supabase ships pgvector 0.7 or later, which has halfvec; the manual step checks
     `select extversion from pg_extension where extname='vector'`.
2. **Hybrid search in SQL.**
   - The function `search_individuals_hybrid(p_query text, p_query_embedding halfvec(3072), p_limit int DEFAULT 20, p_min_similarity double precision DEFAULT 0.15)`.
   - It combines vector cosine rank, full-text rank (a generated `tsvector` on the
     embedding text in `individual_embeddings.search_tsv` with a GIN index,
     `websearch_to_tsquery('simple', p_query)`) and `pg_trgm` name similarity, using
     reciprocal rank fusion `Σ 1/(60 + rank)`.
   - **An exact case-insensitive name match is always first** (keeps today's
     predictable tier).
   - It returns individual rows plus `score` and `match_source`.
   - This replaces the Python cosine and the full-table scans in
     `api/embeddings.py:111-180`.
   - The text-only fallback (no embedding available) calls the same function with a
     null embedding.
3. **Visit-level chunks.**
   - Table `interaction_embeddings(interaction_id PK FK ON DELETE CASCADE, individual_id, embedding halfvec(3072), model, text_hash, created_at)`
     with an HNSW index.
   - The interaction's transcription is embedded in the background after a save.
   - The function `match_interactions(p_query_embedding, p_individual_id uuid NULL, p_limit int)`.
4. **Freshness.**
   - `embedding_service.embedding_text_hash(text) -> str` (sha256).
   - Re-embed only when the hash changes.
   - `scripts/backfill_embeddings.py` gains `--stale`: rows whose
     `source_updated_at < individuals.updated_at` or whose model differs. It uses
     array input (100 texts per call), paginates reads with `fetch_all`, and covers
     interaction chunks too.
   - `generate-all` uses the same code path.
5. **Query embedding cost.**
   - A process-level LRU cache (256 entries, 10 min TTL) keyed on the normalised query.
   - No semantic leg for queries under 3 characters.
   - The Search screen fires semantic search only after a 600 ms pause.
6. **Sensitive fields** (`is_sensitive`, Phase 3) are left out of embedding text.
   Changing the flag marks embeddings stale.
7. **Retrieval service for the assistant** (Phase 5 consumes these exact signatures).
   `backend/services/retrieval.py`:
   - `async def search_people(query: str, limit: int = 5) -> list[dict]`
     (hybrid search; compact person summaries).
   - `async def get_person(individual_id: str) -> dict | None`
     (all fields including sensitive ones, latest 5 interactions, last seen date and area).
   - `async def recent_interactions(individual_id: str, limit: int = 5) -> list[dict]`.
   - `async def most_urgent(near: str | None = None, limit: int = 5) -> list[dict]`.
     Display urgency (`urgency_override` if set, else `urgency_score`); `near` is
     resolved to a centre by `services/sf_neighborhoods.py: def resolve_area(name: str) -> tuple[float, float, float] | None`
     (lat, lng, radius_m), filtered by `last_location` distance using the haversine
     formula in SQL, with no PostGIS.
   - Every result carries `last_seen` (the newest interaction's `created_at`), not
     `updated_at`.
   - Values are clipped with `field_registry.clip_value` (today's `context_service._clip`,
     moved). `retrieval.py` imports nothing from `context_service`, which Phase 5 deletes.
   - `services/sf_neighborhoods.py` is a static dict of about 40 SF neighbourhoods
     with centroids and radii (Mission, Tenderloin, SoMa, Civic Center, Haight, ...)
     and their common aliases.

## Phase 5: voice and audio

Plan: `2026-10-23-05-voice-audio.md`. Mobile, plus the backend proxy. Needs a
native rebuild (`npx expo prebuild --platform ios`); device checks go into the
manual-steps file.

1. **Move from expo-av to expo-audio** (expo-av is removed in SDK 55).
   - Install the SDK 53-compatible version with `npx expo install expo-audio`.
   - Migrate `ModernAudioRecorder.tsx`, `ModernVoiceAssistantScreen.tsx` and
     `utils/audioProcessor.ts`, then remove `expo-av`.
2. **One owner for the audio session.**
   - `mobile/services/audioSession.ts` exposes:
     - `acquireRecording(owner: string): Promise<() => Promise<void>>` sets the record
       mode and returns a release function that restores playback mode;
     - `acquirePlayback(owner: string): Promise<(() => Promise<void>) | null>` returns
       null while a recording holds the session;
     - `isRecordingActive(): boolean`;
     - `onChange(listener): () => void`.
   - Recording has priority. No other file calls `setAudioModeAsync`.
   - The Record tab's release restores playback mode, which fixes the Record tab never
     resetting the mode.
3. **The recorder reads its own status.**
   - Duration comes from the recorder's status (`durationMillis`), not `setInterval`.
   - On an interruption (`isRecording` going false without the worker stopping), stop,
     keep the audio so far, and show
     `"Recording was interrupted at m:ss. You can keep what was recorded or record again."`
4. **Record at 16 kHz mono AAC, 32 kbps**, matching the assistant. Update CLAUDE.md's
   recording rule.
5. **Streaming reply playback.**
   - Play each `response.output_audio.delta` as it arrives through a PCM buffer queue
     (preferred library: `react-native-audio-api`; Task 1 of the plan confirms a
     version compatible with RN 0.79 / Expo 53 and its queue API before building on it).
   - Show the transcript as it streams.
   - Remove the WAV-file path (`createWavFile`, the cache-file write).
   - Keep the per-item buffering rule (C-26), focus gating and generation cancellation (I-2).
6. **Stream the mic over the existing WebSocket.**
   - Capture PCM16 at 24 kHz (the same library's recorder if it exists, else the Task 1
     fallback) and send `input_audio_buffer.append` frames of about 100 ms (already
     allowlisted).
   - Server VAD creates the response.

## Phase 7: async recordings and an offline queue

Plan: `2026-10-23-07-async-recordings.md`. Backend, SQL and mobile.

1. **A recordings job table.**
   - `recordings(id uuid PK, user_id, device_id, client_recording_id uuid UNIQUE, status text CHECK in ('queued','transcribing','extracting','checking_duplicates','ready','failed'), storage_path text, duration_ms int, location jsonb, transcription text, result jsonb, error text, attempts int DEFAULT 0, created_at, updated_at)`.
   - A private Supabase Storage bucket `recordings` (manual step).
2. **`POST /api/recordings` (multipart).**
   - Fields: `audio` (the m4a file), `client_recording_id`, `duration_ms`, `location`
     (JSON).
   - It stores the file in Storage, inserts a row, and returns **202**
     `{id, status}`. A repeated `client_recording_id` returns the existing row.
   - Body cap 8 MB, with the same M4A and duration checks as Phase 1.
   - Rate-limited like transcribe.
3. **An in-process worker.**
   - Started in FastAPI `lifespan`, polling every 2 s.
   - Claims one job at a time with the function `claim_recording_job() returns setof recordings`
     (`FOR UPDATE SKIP LOCKED`, `status='queued'` or stale in-progress older than 5 min,
     `attempts < 3`).
   - Runs the existing stages (transcribe, then extract, then duplicate check),
     **saving the transcription after the first stage** so a retry doesn't pay for it
     again. Writes `result` (the same shape as today's `TranscribeResponse`) and sets
     `ready`, or `failed` with a safe message.
   - Concurrency 2 (env var). One process stays deliberate.
4. **`GET /api/recordings/{id}`** returns the status and result. `GET /api/recordings?status=ready`
   lists the caller's ready drafts. `DELETE /api/recordings/{id}` removes the row and
   the Storage file after a save or discard.
5. **Keep `/api/transcribe`** for one release, marked deprecated in README. The app
   stops calling it.
6. **The mobile offline queue.**
   - `mobile/services/recordingQueue.ts`. Each finished recording is moved to
     `documentDirectory/recordings/<client_recording_id>.m4a`. Metadata (id,
     duration, location, created_at, state) lives in `expo-sqlite`. The id comes from
     Phase 2's `newRequestId()`.
   - **No transcripts or case data in the queue**: only audio plus location, until the
     server has it.
   - Upload with `FileSystem.uploadAsync(..., {uploadType: MULTIPART, sessionType: BACKGROUND})`
     when NetInfo says the phone is online, retrying with backoff.
   - Delete the local file once the server returns 202.
   - Uploads also restart on app launch and when the app returns to the foreground.
7. **Drafts to review.**
   - The Record screen shows the current recording's status ("Uploading", "Queued:
     no connection", "Transcribing", "Ready to review") and polls
     `GET /api/recordings/{id}` with TanStack Query (Phase 6) every 2 s while it's in progress.
   - A "Drafts" list (a badge on the Record tab) shows ready recordings to review later.
   - Reviewing a draft opens `TranscriptionResults` exactly as today. A save or discard
     deletes the recording.
8. **The privacy of audio at rest:** files in `documentDirectory` get iOS Data
   Protection (`NSFileProtectionComplete` set through an entitlement in `app.json`, a
   manual prebuild step). The server's Storage file is deleted after save or discard,
   and `recordings` rows older than 7 days are purged (a function plus a commented
   pg_cron line).
