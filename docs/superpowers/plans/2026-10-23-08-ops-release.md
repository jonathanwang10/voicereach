- Produces (`backend/services/request_log.py`):
  - `REQUEST_ID_HEADER = "X-Request-Id"`; `SUMMARY_LOGGER = "voicereach.request"`
  - `@dataclass class RequestLog: request_id: str; timings: dict[str, int]; usage: dict[str, dict[str, int]]`
  - `def current_log() -> RequestLog | None`
  - `def stage_timer(name: str) -> ContextManager[None]`: adds elapsed whole ms to `timings[name]`, summing repeats; a no-op outside a context
  - `def record_usage(kind: str, source: Any) -> None`: `source` is a response with `.usage`, a usage object or a dict; sums any int `prompt_tokens`, `completion_tokens`, `input_tokens`, `output_tokens`, `total_tokens` into `usage[kind]`; a no-op for a missing usage or outside a context
  - `def log_context(request_id: str | None = None) -> ContextManager[RequestLog]`: for non-HTTP work (a worker job, a WebSocket session)
  - `def emit_summary(event: str, log: RequestLog, **fields) -> None`: one INFO record on `SUMMARY_LOGGER`, message `event`, `extra={"summary": {...}}`. Allowed field names: `SUMMARY_FIELDS = {"method", "route", "status", "duration_ms", "job_id", "job_status", "close_code"}`. Any other name raises `ValueError`, so a new field can't smuggle in data unreviewed.
  - `class RequestLogMiddleware` (pure ASGI, HTTP only)
  - `class JsonFormatter(logging.Formatter)`
- Produces (`backend/main.py`): `def configure_logging(level_name: str | None = None, log_format: str | None = None) -> None`

- One `ContextVar[RequestLog | None]`. The middleware and `log_context` set it and reset it in `finally`. Stages mutate the same `RequestLog` object, so writes from threadpool code (anyio copies the context) are seen.

Never format the traceback or the exception message: a message can echo the data that was sent.

## Deviations from roadmap

1. **The `db` job runs `supabase db start` in a throwaway `supabase init` directory, not `supabase start` in the repo.** The repo has no `supabase/config.toml`. Run from the repo, the CLI would apply `supabase/migrations/` and `seed.sql` itself, before `schema.sql`, and those migrations are upgrades that need the base tables. The tests use psycopg, so only Postgres is needed. The job still applies `schema.sql`, then every migration twice, then runs `pytest -m db`. It also adds an upgrade-path pass from `ce238db:supabase/schema.sql`.
2. **Mobile Sentry has no Expo config plugin and uses `enableNative: false`.** Native crash reports and native network breadcrumbs (request URLs with `?search=` names) don't go through the JS `beforeSend`, and the plugin's source-map upload would need a `SENTRY_AUTH_TOKEN` in every build. Result: JS errors only, minified stacks. Trigger to revisit: wanting native crash reports, together with native-side scrubbing.
3. **The backend also reads `SUPABASE_PUBLISHABLE_KEY`, falling back to `SUPABASE_ANON_KEY`.** The roadmap names only the secret key for the backend. `auth.py`'s `get_user` client still needs a public key, and the anon key ends with the other legacy keys.
4. **JWKS fallback rules.** Besides a symmetric `alg`, a token with no `kid` or an unparseable header also goes to `auth.get_user`, which keeps today's behaviour. An unreachable JWKS endpoint falls back to `get_user` instead of failing. A JWKS answer that rejects the token is a 401 and does not fall back.
5. **The eas.json `development` profile omits `developmentClient`.** `expo-dev-client` isn't installed. It is a Debug simulator build that loads JS from Metro, the same as `npx expo run:ios`.
6. **The fake-OpenAI mode doesn't cover the realtime WebSocket.** The load test doesn't exercise the assistant, and README says so.
7. **(Task 2, during execution) An unhandled 500 has no `X-Request-Id` header.** Starlette's
   `ServerErrorMiddleware` answers it outside every user middleware; the summary line and the
   Sentry event still carry the id, so the capture test checks the tag's form, not equality with
   a header. sentry-sdk 2.73 warns that `send_default_pii` is deprecated in favour of
   `data_collection`; the plan's option (and its test) is kept, since it still turns PII off.
